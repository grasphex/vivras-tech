firewalld｜同じ80/tcpでも通る通信・通らない通信がある理由

「80/tcpを許可したのに、つながらない」。まず確認すべきなのは、その通信にどのが使われているかです。

点線の用語をタップすると説明が開きます。

01 / なぜ必要？

同じサーバーでも、接続する場所によって許可を変えたい。

例えば社内からの管理接続は許可し、インターネットからの不要な接続は防ぎたい。Linuxのは、こうした通信のルールを分かりやすく管理するサービスです。

答え：通信を受け取ったら、①適用するzoneを決める → ②そのzoneの許可設定に合うか調べる。そのため、同じでも適用zoneが違えば結果が変わります。

03 / 一つの例を最後まで追う

publicで80/tcpを許可したのに、なぜinternal側では通らない？

以下のように設定した架空のサーバーを考えます。ネットワークの接続口eth0はinternal、eth1はpublicに割り当ててあるものとします。

図の流れを一つずつ確認
  1. 接続口を確認：届いた通信の送信元やネットワークの入口（）への割り当てから、使うzoneを決めます。
  2. そのzoneを確認：internalに80/tcpの許可がなければ、publicの許可は使われません。zoneごとに設定が独立しているためです。
  3. ポートと方式を照合：80/tcpを許可した場合でも、が自動で許可されるわけではありません。

この図は、新規の受信通信・単純な許可ルールを仮定。実際はzone target、rich rule、policy、接続状態なども影響します。インターフェースだけでなく送信元アドレスにもzoneを割り当てられます。

04 / 条件を変えて納得

同じ80/tcpを、違うzoneへ通してみる。

操作して結果を確かめる
この例の設定を切り替える実機の設定は変わりません

許可された場合でも、Webサーバーが起動していない・経路が壊れている等の理由で接続できないことはあります。

コマンドで確認
# サービスの起動状態
sudo firewall-cmd --state
# どの接続口・送信元にどのzoneが使われるか
sudo firewall-cmd --get-active-zones
# internalに登録した許可（services / ports 等）
sudo firewall-cmd --zone=internal --list-all
# publicに登録した許可
sudo firewall-cmd --zone=public --list-all

--get-active-zonesで「通信に適用されるzone」を見てから、--list-allのservices（サービス名）とports（ポート番号・方式）を読みます。設定したzoneが実際の通信に適用されていなければ、許可を増やしても直りません。

実際に80/tcpの許可を追加するときは？ 
# 一時的な設定（実行中の設定だけ）
sudo firewall-cmd --zone=internal --add-port=80/tcp
# 永続設定（次の再起動後も残したい場合）
sudo firewall-cmd --permanent --zone=internal --add-port=80/tcp
# 永続設定を実行中にも反映
sudo firewall-cmd --reload

--permanentだけではすぐ反映されず、--reloadで適用されます。reloadは別の一時設定に影響することがあります。接続が切れると困るリモート機器では、事前確認が必要です。

3問で理解度を確認
Q1. publicに80/tcpを許可すれば、internalでも使える？

使えません。別のzoneの許可設定だからです。internal側の通信にはinternalのルールを確認します。

Q2. 80/tcpを許可すれば80/udpも許可される？

いいえ。番号が同じでもTCPとUDPは別の通信方式です。

Q3. firewalldが通信を許可したら、Webに必ずアクセスできる？

いいえ。Webサーバーが動いているか、別の通信制御やネットワーク経路に問題がないかは別に確認します。
