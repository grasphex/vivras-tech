# VIVRAS Tech｜制作ルール
**正本：** [Notion｜運営・編集方針](https://app.notion.com/p/419636f0a707814d96fcc19f422e51b3)

## 価値
SEとしての仕事を原点に、技術・教養・暮らし・経験・考察を記録する個人メディア。**学んだことを、他人が一瞬で理解できる形にする。**「Tech」は発信ジャンルの制限ではない。

## 記事の5原則
1. **冒頭1画面に結論＋俯瞰図。** 主題・構成・因果関係が10秒でつかめる。
2. **総論→各論。** 重要な前提から説明し、知らない用語や論理の飛躍を残さない。
3. **最大限短く。** 前置き、重複、抽象的な標語、用のない英語・注釈・アイコン・カードを削る。条件・例外・出典は残す。
4. **視覚で伝える。** 図、比較、余白、文字の強弱が情報そのものを説明する。操作・アニメーションは理解に役立つ場合だけ使う。
5. **初見の第三者で検証。** 「何を学べるか」「関係が分かるか」「読むべき情報が瞬時に見つかるか」をPC・375pxスマホで確認。未達なら未完成。

## 編集の順序
目的の一文 → 全体像のラフ図 → 見出しと論理構成 → 一次資料の確認 → HTML/CSS/JS → 初見レビュー → 削除・修正 → 公開・表示検証。

記事構成は原則「要点と図 → 必要な仕組み・根拠・具体例 → 留意点・出典」。**不要な章は作らず、記事ごとに最適な構成を選ぶ。** 詳しいコマンドやシミュレーションはIT記事で必要な場合に置く。体験・意見・仮説は事実と明確に区別する。

## デザイン
- [CSS Design Awards 2025 WOTY](https://www.cssdesignawards.com/blog/2025-website-of-the-year-winners/430/) の Dropbox Brand、[The Creative Website Manual](https://www.cssdesignawards.com/sites/the-creative-website-manual/48438/) など、受賞実例のタイポグラフィ・グリッド・導線を研究する。
- **受賞サイト風の装飾が目的ではない。** 視線の最短経路を作り、言葉と図が1つのメッセージに収束するように独自設計する。コード・画像の無断転載はしない。
- 安易な均一カード、青紫グラデーション、汎用アイコン、不要なアニメーションを避ける。文字の可読性、コントラスト、レスポンシブ、低モーションを維持する。

## 公開前の最低条件
- **中身：** 正確さ、一次資料、用語の前提、事実と推測の区別、著作権・会社機密・個人情報の除去。本人や家族の機微情報は明示的な許諾なしに公開しない。
- **見た目：** 冒頭10秒で主題と関係が分かる／文章が最少／375pxで横スクロールなし／リンクと操作が機能する。
- **構造：** 新規記事は `content/<slug>.html`。単体HTMLに `lang="ja"`、`title`、`description`、`category`、`published`、`../assets/site.css`、`<main>` を含める。ファイル名は英小文字・数字・ハイフン。
- **運用：** GitHubに反映後、ビルド・デプロイ・公開URL・スマホ画面を別々に確認し、未確認を成功と呼ばない。記事の修正は差分の継ぎ足しでなく完成版へ置換する。

**合格基準：** 「文章が正しい」だけでなく「見た瞬間に内容が分かる」。それまで叩き台として改稿する。

## 雇用・税制の図解ルール（2026-11-15）
- 給与総額が下がる図には**社員数×1人当たり給与**を併記し、賃下げ・解雇・労働時間減のどれが原因かを明示する。
- AI導入後に**人員削減する場合・雇用維持する場合**を区別し、売上・AI利用費・給与・利益の計算を一致させる。
- AI導入で給与由来の税収が必ず減ると断定しない。法人税と給与由来の税収を区別し、社会保険料は税金と混同しない。
- 日米の解雇規制を比較する際は米国のat-willの例外と日本の労働契約法16条を併記する。いずれも絶対的に断定しない。
- 法案の提出者・課税主体・課税標準・財源使途を一次資料で確認し、別法案や政策提言と混同しない。

## ニュース記事の主題固定（2026-11-15）
- まず「何のニュースか」「政策・法案の狙い」「誰が・何に・どう課税」を、提出者の一次資料で確定する。
- タイトルとファーストビューには必ずニュースの主題を置く。背景条件や派生問題（例：AI導入後の雇用削減・日米の解雇規制）は、主題に従属する位置にする。
- **仮説と政策目的の混同は禁止。** 例：「所得税が減り得る」は背景仮説だが、「減収の一対一補填」が法案の目的とは限らない。
- 異なる法案は、提出者・納税義務者・課税対象・税収の使い道を横並びで確認する。提言者と法案提出者も区別する。
- 図が誤解を生む場合は、見栄えより先に因果関係と課税主体を修正。既存記事のレビューでは「主題から逸れていないか」を最優先の自己検証項目にする。

## 法案・政策の解説：政策ロジック必須（2026-11-15）
- **法案ごとに独立して**「問題認識（誰が何を懸念）→政策判断（何を変えたい）→実際の条文上の仕組み（誰が・何に課税）→税収の使途（具体的な支援）」を一次資料で確認し、俯瞰図にも示す。
- 各議員の「発言による目的」と「条文にある仕組み」を区別する。編集上の因果関係整理なら、その旨明記する。法案同士の共通点と違いを早い段階で見せる。
- 背景の補助条件（雇用維持・人員削減・他国の法制）は主題に従属させる。原因と結果の途中を省かず、記事の主題から逸れない。
- 公開前に読者の質問「なぜその手段が必要？既存の制度ではだめ？集めた税金を何に使う？」へ1画面の要約＋各論で答えられるか確認。

## 初学者の理解負荷を下げる（2026-11-15）
- 社会人1〜2年目でも分かる言葉を使う。法案名など固有名詞を除き、専門用語は平易な日本語を優先する。使う場合はその場で「何のことか」を短く説明し、必要なら用語一覧を用意する。
- 「利益を還元」「労働者に投資」「再分配」のような抽象語だけで説明を終えない。**誰が払う→どこに集まる→誰が何を受け取るか**を一枚の図と身近な例で表現する。
- 似た法案でもそれぞれの狙いを分け、「仕事を増やす」対「次の仕事へ進む人を支援する」のように区別する。法案の厳密な条件と説明用の簡略図は混同しない。
- 図解と本文は、ページを開いたときの可読性・スマホ幅・見出しと説明の一貫性を自己レビューする。

## 初見の読者に必要な前提を欠かさない
- 記事は**検索から単独でたどり着いた読者**が理解できることを前提とする。新聞記事、元チャット、過去の改訂版を読んだ前提の表現（例：「新聞に出てきた」「さっきの」「前の版」「今回直した」）を禁止する。
- 人名や制度名が初登場する際は、何者か／どの立場かを短く説明する。政策提唱者と法案提出者は混同しない。
- 公開前に固有名詞の初出と参照先を確認し、記事内の情報だけで意味が通るか検証する。

## 補足人物・制度の登場理由（2026-11-15）
- 人物を追加する前に「なぜ本題に必要か」を一文で説明する。**人物紹介やQ&Aだけを唐突に差し込まない。**
- 主役と補足を視覚・文章で区別する。記事の主題（法案など）の説明が終わった後に「関連する別の提言」として配置し、共通点・違い・関係性を簡潔に明記する。
- 初見の第三者が、前の段落から次の段落に進む理由を理解できるか点検する。記事を読まずに直前の説明だけを見ても「なぜこの人物？」となるなら再編集する。

## 政策提言の因果関係（2026-11-15）
- 「Aに課税し、Bの負担を軽くする」など対になる政策は、**誰の費用がどう変わるか → 行動の選び方がなぜ変わるか**を間に挟む。結論だけ書かない。
- **会社側の給与関連負担**と**従業員本人の所得税**は分ける。税と保険料、税を課される人と最終的に費用を負担する人も区別する。
- 税がAIの販売価格・利用料金に反映されるか、雇用が増えるかは条件次第。必然の結果として書かず、「反映されれば」「可能性」などで示す。
- 補足人物の説明でも、その人物自身の一次資料に基づき、問題→比較→提案→期待する効果を自立した論理で説明する。

## 2階層のカテゴリー管理（2026-11-15）
- **技術**（Linux、ネットワーク、クラウド等）、**社会・教養**（政治・経済、地理・歴史等）、**健康・暮らし**（脳・健康、妊活、生活等）。小分類は`scripts/build.py`のマッピングで管理。
- 小分類は実際に記事があるときだけ表示する。妊活など将来の領域を空記事やダミーの一覧として公開しない。
- 記事の`meta name="category"`には小分類を設定する。記事の公開URL・canonicalは分類変更で変更しない。全記事に分野横断ヘッダー、パンくず、同分野の一覧への戻りリンクを用意する。
- **既存記事にも新基準を適用**：ファーストビューに「結論＋その記事固有の因果図」を置き、同じ説明の重複は削除する。単なる3カラムカードや一般論の図は避け、内容固有の数字・構造・分岐を描く。
- 技術記事の図は、通常ケースと例外を区別し、条件を明記する。firewalldのzoneやDNSのキャッシュ、Linuxのマウントは実機状況によって変わるため、例を一般則と混同しない。
- 医療・健康の記事は教育用であることを明記し、研究上の仮説を確定原因・診断法として断言しない。
- カテゴリー記事から他カテゴリーへ最短で移動できるよう、PC・スマートフォン両方で確認する。

## 技術記事の論理設計・自己レビュー（2026-11-15）
- 参考にする構成：CloudflareのDNS解説（読者の目的→登場人物→一つの問い合わせを追う）、DigitalOceanのfirewalld入門（前提→設定対象→具体例→確認）、Linuxのmanページ（`mount`の接続元と接続先、`remount`の意味）。説明の事実は一次資料を優先する。
- 章を機械的に8個に揃えない。**困りごと → 一文の結論 → 必要な用語（絞る）→ ただ一つの具体例を最後まで → 条件が変わった場合 → 実機で確認 → 誤解・根拠**。意味のない図や重複した手順リストは削除する。
- 図の前に登場する用語を短く定義する。図の直後に**どの前提なら・なぜ矢印の次の状態になるか**を一文ずつ書く。動く図が必要な場合も操作しない初期状態で結論が読めること。
- 技術固有の誤解を必ず検査する：
  - Linux：ブロックデバイス名とディレクトリの違い、マウント＝コピーではない、ro/rwと別のアクセス権限を混同しない。
  - firewalld：zoneの名称から許可ルールを決めつけない。通信へのzone割当、zone内のサービス/ポート設定、TCP/UDP、runtime/permanentを分ける。
  - DNS：端末と再帰DNSの役割、ルート/TLDの案内と権威DNSの回答、キャッシュ、DNS後のWeb通信を区別する。
- ただし知識を詰め込みすぎない。読者が読む理由のない仕様や例外は本文の末尾に短く記載し、出典へのリンクで補う。
- レビューでは「初見の社会人1年目が各節を読み、なぜ次の説明に進むかを説明できるか」を最優先にする。**見た目と字数のチェックだけでは説明の正確さは保証できない**。

## 読者の操作で開く解説（2026-11-15）
- **用語集を独立した長い章として置かない。** 初登場する専門用語は`<button class="vterm" type="button" data-explain="...">用語</button>`で本文に組み込み、タップ・クリックで短い説明を開く。説明は原則1〜2文。
- 必ず記事冒頭の核心と1枚の図はそのまま見せる。**内容を理解するために必須の事実を、閉じた詳細パネルの中だけに隠さない**。
- 操作例・法案条文の細部・参考資料・Q&A・関連人物などは`<details class="article-expand"><summary>...</summary>...</details>`で必要に応じて表示する。開かなくても記事の結論が理解できること。
- 用語補足は小さなオーバーレイで示し、ページが上下に跳ねないようにする。モバイルでは下部に表示、1件ずつ、もう一度タップ／外側タップ／Escape／閉じるボタンで閉じられること。
- `assets/terms.js`・`assets/site.css`を共通利用する。記事ごとに独自のツールチップJSを複製しない。用語の説明は事実・出典の範囲に沿い、過剰な断定を避ける。
- 記事公開時は構造テスト・動作テスト・スマートフォンの横幅・スクロール量・核心の可視性を確認する。未確認の実表示を「確認済み」としない。
